# اتصال اختیاری دادهٔ روزانه به تحلیل

مالک درخواست فعال‌سازی را مطرح کرد و تأیید کرد که معاملات کوتاه‌مدت نویز دارند. این تغییر، اتصال اختیاریِ داده‌های عمومی به تحلیل Kimi را آماده می‌کند؛ فعال‌سازی اثر روی حساب واقعی باید توسط مالک انجام شود. در تهیه و آزمون این تغییر، تنظیمات حساب، سرویس معامله‌گر، مدل یا سفارش‌ها دست‌کاری نمی‌شوند.

## قرارداد رفتار

- `context.public_flow_snapshot` به‌صورت پیش‌فرض `null` است؛ رفتار نسخهٔ پایه و پیام مدل تغییر نمی‌کند.
- با تعیین مسیر مطلق `snapshot.json`، ساخت context کامل یک فایل عمومیِ محدود به ۵۱۲ کیلوبایت را می‌خواند. دریافت شبکه، فراخوانی مدل و بیدارسازی جدیدی اضافه نمی‌شود.
- فقط فشار معاملات **۲۴ساعته** با وضعیت آماده، پوشش پیوستهٔ کامل و دریافت حداکثر ۹۰ ثانیه قبل وارد می‌شود. بازه‌های ۵ و ۱۵ دقیقه، ۱ و ۴ ساعت در گزارش آزمایش باقی می‌مانند و وارد تصمیم نمی‌شوند.
- تغییر عرضهٔ USDT و USDC در بازه‌های روزانه، هفتگی و ماهانه، با سن دریافت حداکثر دو ساعت می‌آید. زمان انتشار DefiLlama نامعلوم باقی می‌ماند؛ این داده شاخص نقدینگی بالقوه است، نه اثبات خرید یا واریز به صرافی.
- `BTC_USDT` با نام و واحد خودش می‌آید؛ به `BTC_IRT` تبدیل یا تغییر نام نمی‌یابد. بازارهای نامرتبط با universe ربات حذف می‌شوند. هیچ جمعی از تومان و تتر ساخته نمی‌شود.
- دفتر سفارش نمونه‌برداری‌شده به سیگنال مستقل تبدیل نمی‌شود؛ دفتر IRT موجود همچنان نقش نقدشوندگی و اجرا را دارد.
- محاسبات دلتا و نسبت خرید دوباره کنترل می‌شوند. دادهٔ خراب، نامتناهی، با کلید تکراری، زمان آینده، پوشش جعلی یا فایل غیرعادی به وضعیت «ناموجود» می‌رود. متن آزاد منبع وارد پیام مدل نمی‌شود.
- نبود داده باعث صفرشدن فشار یا توقف تحلیل اصلی نمی‌شود. داده‌های کمکی در صورت کمبود ظرفیت context، پیش از داده‌های موجود حذف می‌شوند.
- `P RULE`، احتمالات مجاز، قوانین خروج، اندازه‌گذاری، زمان‌بندی و هزینه‌ها تغییر نکرده‌اند. این شواهد، مزیت سودآور اثبات‌شده یا مبنای مستقل خرید نیستند. Kimi باید بازار، بازه و مقدار دقیق را در استدلال خود ذکر کند.

## آماده‌سازی توسط مالک

وضعیت تحویل در ۲۰۲۶-۱۰-۱۰: سرویس عمومی `bitpin-flow-public.service` نصب و فعال شد؛ بنابراین گام‌های ۲ و ۳ در همین محیط قبلاً انجام شده‌اند و نباید دوباره اجرا شوند. نمونهٔ کدِ اتصال آماده است، اما در مسیر معامله‌گر واقعی نصب نشده و `kimi.json` واقعی تغییر نکرده است. جمع‌آوری عمومی به‌تنهایی به معنی فعال‌شدن تصمیم‌گیری مالی نیست.

دستورهای زیر برای اجرای **دستی مالک** هستند. اسکریپت update ممکن است سرویس واقعی را راه‌اندازی مجدد کند؛ اتصال به حساب و مرحلهٔ `confirm-live` را خود مالک انجام می‌دهد. این راهنما مجوز اجرای خودکار آن‌ها توسط دستیار نیست.

۱. نسخهٔ جدید را از شاخهٔ تغییرات بازبینی‌شده در مسیر مستقل قرار دهید. ابتدا آزمون‌های آفلاین را اجرا و سپس مطابق `DEPLOY_FA.md` نسخهٔ جدید را نصب کنید. پیش از نصب نسخهٔ جدید، کلید جدید را به `kimi.json` اضافه نکنید؛ نسخهٔ قبلی آن را نمی‌شناسد.

```console
python3 -B -m unittest discover -s tests
sudo bash deploy/update.sh
```

۲. برای جمع‌آوری عمومی یک کاربر سیستمی مجزا به نام `bitpin-flow` و گروه هم‌نام، بدون shell تعاملی، بسازید؛ اگر این نام از قبل وجود دارد، مالکیت و کاربردش را پیش از استفاده بررسی کنید. فقط در صورت نبودن این کاربر:

```console
sudo useradd --system --user-group --home-dir /nonexistent --shell /usr/sbin/nologin bitpin-flow
```

۳. از ریشهٔ نسخهٔ جدید، کد عمومی و unit مستقل را نصب کنید. وضعیت این سرویس فقط دادهٔ عمومی است و خواندنی برای سایر کاربران محلی؛ نوشتن فقط برای کاربر جمع‌آورنده مجاز است. مسیرهای حساب واقعی در sandbox سرویس غیرقابل دسترسی‌اند.

```bash
sudo install -d -m 0755 /opt/bitpin-flow-public/bitpin /opt/bitpin-flow-public/scripts
sudo install -m 0644 bitpin/{__init__,flow_features,flow_public,flow_shadow,flow_report,flow_context}.py /opt/bitpin-flow-public/bitpin/
sudo install -m 0644 scripts/flow_shadow.py scripts/preview_flow_context.py /opt/bitpin-flow-public/scripts/
sudo install -m 0644 deploy/bitpin-flow-public.service /etc/systemd/system/bitpin-flow-public.service
sudo systemctl daemon-reload
sudo systemctl enable --now bitpin-flow-public.service
```

۴. به جمع‌آورنده حداقل ۲۴ ساعت پوشش پیوسته بدهید. قطعی یا گم‌شدن هم‌پوشانی زمان گرم‌شدن را دوباره شروع می‌کند. فایل پیش‌نمایش را با همان کاربر معامله‌گر بخوانید؛ این دستور فقط فایل عمومی را می‌خواند و مدل یا حساب را صدا نمی‌زند:

```console
sudo -u bitpin python3 -B /opt/bitpin-flow-public/scripts/preview_flow_context.py --snapshot /var/lib/bitpin-flow-public/snapshot.json
```

خروج صفر فقط موفقیت خواندن snapshot است؛ آماده‌بودن فشار روزانه با وجود `markets.<market>.daily` مشخص می‌شود. پیش از وجود آن، فشار روزانه وارد تحلیل نمی‌شود. آزمون کوتاه قبلی فقط مسیر دریافت را تأیید کرد؛ اثر بر بازده، کارمزد و لغزش هنوز مقایسه نشده است.

۵. پس از تصمیم مالک برای اتصال به حساب واقعی، ابتدا سرویس معامله‌گر را متوقف و از تنظیمات نسخهٔ پشتیبان بگیرید. `confirm-live` تعاملی کنار سرویس روشن اجرا نمی‌شود. هنگام توقف، نظارت و خروج‌های نرم‌افزاری ربات اجرا نمی‌شوند؛ سفارش‌های موجود در صرافی همچنان ممکن است اجرا شوند.

```bash
flow_backup="/etc/bitpin-bot/kimi.json.before-public-flow-$(date -u +%Y%m%dT%H%M%SZ)"
sudo cp -a /etc/bitpin-bot/kimi.json "$flow_backup" &&
sudo systemctl stop bitpin-bot.service
```

فقط پس از موفقیت این دستورات، این کلید را به شیء `context` در تنظیمات موجود اضافه کنید و بقیهٔ تنظیمات را حفظ کنید:

```json
"public_flow_snapshot": "/var/lib/bitpin-flow-public/snapshot.json"
```

سپس روند تأیید خود پروژه را شخصاً اجرا کنید:

```console
sudo bitpin-bot check &&
sudo bitpin-bot confirm-live &&
sudo systemctl start bitpin-bot.service
```

عبارت تأیید را مالک وارد می‌کند؛ هیچ کلید، token یا فایل env لازم نیست در گفتگو ارسال شود. اگر هر مرحله خطا داد، به مرحلهٔ بعد نروید. برای غیرفعال‌سازی، ابتدا سرویس معامله‌گر را متوقف کنید، مقدار کلید را `null` کنید و همان روند check، تأیید و start را طی کنید. توقف سرویس عمومی نیز داده را حداکثر پس از ۹۰ ثانیه از مصرف خارج می‌کند، اما برای حذف قطعی بخش context، تنظیم را خاموش کنید.

## بازبینی و آزمون

تست‌های `tests/test_flow_context.py` شامل نمونه‌های دست‌محاسبه، رد دادهٔ خراب و زمان/پوشش ناسازگار، جداسازی واحدها، خواندن اختیاری، ورود به پیام مدل بدون فراخوانی مدل، حفظ قاعدهٔ خرید و اولویت ظرفیت context هستند. نتایج نهایی اجرا و محدودیت‌های باقیمانده در گزارش تحویل ثبت می‌شوند.

نتیجهٔ نهایی ۲۰۲۶-۱۰-۱۰:

- مجموعهٔ کامل: ۱۷۸۹ تست روی Python 3.7 و 3.14، بدون شکست، با ۲۱ مورد اجرا‌نشده مطابق شرایط مجموعه.
- آزمون‌های قابلیت جریان و اتصال جدید روی Python 3.12 سرور: ۴۷ تست موفق؛ ۱۵ تست آن مخصوص اتصال context است.
- بازبینی مستقل یک ایراد زمان‌سنجی پیدا کرد: زمان سپری‌شده حین ساخت تحلیل در سن snapshot لحاظ نمی‌شد. دو حالت «تازه‌شدن فایل در حین ساخت» و «کهنه‌شدن فایل در حین ساخت» پیش از اصلاح شکست خوردند و پس از اصلاح پاس شدند. اکنون سن دریافت هنگام مصرف محاسبه می‌شود و ساعت شبیه‌سازی نیز حفظ می‌شود. مورد بازِ مهم یا بحرانی باقی نماند.
- واحد systemd از نظر ساختار با `systemd-analyze verify` بررسی شد. سرویس عمومی با کاربر مجزا، مسیرهای حساب غیرقابل دسترسی و محدودیت منابع اجرا شد. دو نوبت نخستِ دریافت هر پنج بازار و DefiLlama موفق بودند.
- پیش‌نمایش عمومی با کاربر معامله‌گر قابل خواندن بود؛ هیچ مدل یا حسابی فراخوانی نشد. پنجره‌های روزانه به‌درستی `warming_up` ماندند و اعداد فشار ناقص وارد context نشدند؛ دادهٔ نقدینگی معتبر موجود بود.
- ربات واقعی با همان فرایند قبلی فعال ماند. سودآوری و اثر بر تصمیم واقعی هنوز آزموده نشده و اتصال مالی فعال نشده است.

منبع تنظیم مالکیت و مجوزهای دایرکتوری سرویس: [مستندات رسمی systemd، StateDirectory و StateDirectoryMode](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml).
